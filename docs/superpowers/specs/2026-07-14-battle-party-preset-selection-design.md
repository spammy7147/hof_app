# 전투 파티 프리셋 선택 UI 설계

## 목표

전투 탭에서 맵을 펼쳤을 때 캐릭터 슬롯 5개를 바로 노출하지 않는다. 먼저 저장된 파티 프리셋을 검색해서 선택하게 하고, 프리셋을 사용하지 않을 때만 **캐릭터 직접 선택**으로 5인 파티를 구성한다.

사용자 흐름은 다음과 같다.

1. 전투 카테고리와 그룹을 펼친다.
2. 실행할 맵을 펼친다.
3. 검색 가능한 드롭다운에서 파티 프리셋 또는 **캐릭터 직접 선택**을 고른다.
4. 선택된 5인 파티와 패턴을 확인하거나 수정한다.
5. 1회 또는 3회 전투를 실행한다.

## 승인된 화면 구성

맵 아래의 기존 BattleRunPanel 안에 단계형 파티 선택 영역을 둔다. 별도 화면이나 하단 시트로 이동하지 않으며, 현재 전투 트리의 문맥을 유지한다.

초기 상태에서는 다음 항목만 표시한다.

- STEP 1 · 파티 선택 라벨
- 현재 선택값을 표시하는 프리셋 드롭다운 필드
- 프리셋 로딩, 빈 목록 또는 오류 상태

드롭다운을 열면 상단에 검색 입력을 표시한다. 검색 결과에는 프리셋 이름, 멤버 이름 요약, 선택 상태를 표시한다. **캐릭터 직접 선택**은 검색 결과와 분리해 목록 하단에 항상 노출한다.

프리셋 또는 직접 선택이 끝난 뒤에만 다음 항목을 표시한다.

- 캐릭터 슬롯 5개
- 슬롯별 캐릭터 이름, 레벨, 직업
- 슬롯별 저장 패턴 선택
- 출정 인원 수
- 1회/3회 전투 버튼
- 전투 오류와 결과

## 선택 상태와 전환

파티 구성 방식은 세 상태를 갖는다.

- unselected: 아직 구성 방식을 고르지 않은 상태
- preset: 저장된 프리셋을 선택한 상태
- direct: 캐릭터를 직접 선택하는 상태

### 프리셋 선택

프리셋을 선택하면 createPartyFromPreset으로 저장된 멤버와 패턴을 5개 BattlePartyMember 슬롯으로 변환한다. 선택 이후에도 기존 BattlePartySelector를 사용해 캐릭터와 패턴을 임시로 수정할 수 있다. 이 변경은 전투 요청에만 사용하며 저장된 프리셋 자체는 수정하지 않는다.

동기화된 캐릭터 목록에서 사라진 캐릭터가 프리셋에 포함돼 있으면 해당 슬롯을 비운 상태로 표시하고 전투 버튼을 비활성화한다. 사용자가 다른 캐릭터를 넣어 5명을 완성하면 실행할 수 있다.

### 캐릭터 직접 선택

**캐릭터 직접 선택**을 고르면 자동으로 앞의 캐릭터 5명을 채우지 않고 빈 슬롯 5개를 만든다. 사용자가 각 슬롯을 눌러 캐릭터를 지정한다. 중복 캐릭터를 새 슬롯에 지정하면 기존 슬롯에서 제거하는 현재 선택 규칙을 유지한다.

슬롯 5개가 모두 유효한 캐릭터로 채워져야 전투 버튼이 활성화된다.

### 맵 전환

현재 구조처럼 한 번에 하나의 맵만 펼친다. 다른 맵으로 이동하거나 맵을 닫았다가 다시 열면 해당 BattleRunPanel의 임시 파티 선택 상태를 초기화한다. 저장 프리셋 데이터는 다시 사용할 수 있지만 이전 맵의 임시 수정은 보존하지 않는다.

## 검색 동작

검색어는 앞뒤 공백을 제거하고 대소문자를 구분하지 않는다. 다음 텍스트 중 하나에 포함되면 결과에 남긴다.

- 프리셋 이름
- 프리셋에 포함된 캐릭터 이름
- 캐릭터 직업명

검색 결과가 없으면 **일치하는 프리셋이 없습니다.**를 표시한다. 이때도 **캐릭터 직접 선택**은 계속 선택할 수 있다.

## 데이터 흐름

기존 GET /api/party-presets API와 PartyPresetResponse 타입을 그대로 사용한다. 백엔드 변경은 필요하지 않다.

앱의 데이터 흐름은 다음과 같다.

1. App의 기존 listPartyPresets 콜백을 MainScreen과 BattleTabScreen을 거쳐 BattleRunPanel에 전달한다.
2. 맵 실행 패널이 열리면 프리셋 목록을 조회한다.
3. 조회 결과와 검색어로 드롭다운 옵션을 만든다.
4. 선택된 프리셋은 BattlePartyMember 배열로 변환한다.
5. 기존 toRunBattleRequest가 선택된 캐릭터와 패턴으로 전투 요청을 만든다.

같은 화면 세션에서 이미 성공적으로 불러온 프리셋 목록은 재사용해 맵을 바꿀 때마다 중복 요청하지 않는다. 수동 재시도는 조회 실패 상태에서 제공한다.

## 컴포넌트 경계

### BattleTabScreen

- 프리셋 조회 콜백을 받는다.
- 전투 탭에서 사용할 프리셋 목록, 로딩, 오류 상태를 소유한다.
- 열린 맵의 BattleRunPanel에 프리셋 상태를 전달한다.

### BattleRunPanel

- unselected, preset, direct 선택 상태를 소유한다.
- 프리셋 선택을 파티 슬롯으로 변환한다.
- 선택 완료 전에는 5개 슬롯과 실행 버튼을 숨긴다.
- 선택 완료 후 기존 BattlePartySelector와 전투 결과 영역을 렌더링한다.

### BattlePartyPresetPicker

- 검색 입력과 검색 가능한 프리셋 드롭다운을 렌더링한다.
- 프리셋 이름, 멤버, 직업 검색 결과를 계산한다.
- 로딩, 오류, 빈 결과를 표시한다.
- **캐릭터 직접 선택**을 검색 결과 아래에 고정한다.

검색과 선택 로직을 별도 컴포넌트로 분리해 BattleRunPanel이 전투 실행과 결과 표시 책임에 집중하도록 한다.

## 오류와 빈 상태

- 프리셋 조회 중: 드롭다운 필드를 비활성화하고 로딩 문구를 표시한다.
- 조회 실패: 오류 문구와 **다시 시도** 버튼을 표시한다. 직접 선택은 계속 사용할 수 있게 한다.
- 저장 프리셋 0개: **저장된 프리셋이 없습니다.**와 직접 선택 옵션을 표시한다.
- 검색 결과 0개: 검색 결과 안내와 직접 선택 옵션을 표시한다.
- 캐릭터 0개: 기존 동기화 필요 안내를 유지하며 전투 실행을 막는다.
- 선택 프리셋의 일부 멤버 누락: 누락 슬롯을 비우고 사용자가 보완할 수 있게 한다.

## 접근성과 모바일 동작

- 드롭다운 필드와 옵션에 accessibilityRole button과 선택/확장 상태를 제공한다.
- 검색 입력에는 프리셋과 캐릭터를 검색한다는 명확한 placeholder를 제공한다.
- 긴 프리셋/캐릭터 목록은 가상화된 FlatList를 사용한다.
- 드롭다운은 화면 높이를 넘지 않도록 최대 높이를 제한하고 내부 목록만 스크롤한다.
- 캐릭터와 패턴 선택에는 기존 모달과 Pressable 기반 동작을 재사용한다.

## 테스트 전략

구현은 TDD로 진행한다.

1. 프리셋 검색 도메인 테스트
   - 이름, 캐릭터 이름, 직업으로 검색
   - 공백과 대소문자 정규화
   - 검색 결과가 없어도 직접 선택 가능
2. 파티 초기화 테스트
   - 프리셋 선택 시 저장 멤버와 패턴 변환
   - 직접 선택 시 빈 슬롯 5개
   - 동기화 목록에서 누락된 멤버 제거
3. 컴포넌트 구조 테스트
   - 초기 상태에서 슬롯 5개를 렌더링하지 않음
   - 프리셋 또는 직접 선택 후 BattlePartySelector 렌더링
   - 로딩, 오류, 빈 결과 상태와 재시도 노출
4. 화면 연결 테스트
   - App → MainScreen → BattleTabScreen으로 기존 프리셋 조회 콜백 전달
   - 선택한 파티가 기존 전투 요청 변환과 실행 콜백으로 전달
5. 전체 앱 타입 검사와 테스트

## 고려한 대안

### 맵 아래 단계형 드롭다운 — 채택

현재 전투 트리 안에서 맵과 파티의 관계가 유지되고, 프리셋이 많아도 화면을 길게 차지하지 않는다.

### 하단 시트 선택 — 제외

프리셋 선택에 집중하기 쉽지만 맵 문맥이 흐려지고, 직접 선택을 위해 시트 안에서 추가 단계가 필요하다.

### 프리셋 카드 전체 노출 — 제외

프리셋이 적을 때는 빠르지만 목록이 늘면 전투 트리가 지나치게 길어지며 사용자가 요청한 검색 가능한 드롭다운과 맞지 않는다.

## 완료 기준

- 맵을 펼친 직후 캐릭터 슬롯 5개가 보이지 않는다.
- 프리셋을 이름, 캐릭터 이름, 직업으로 검색하고 선택할 수 있다.
- 직접 선택 옵션으로 빈 슬롯 5개를 열어 캐릭터와 패턴을 지정할 수 있다.
- 프리셋 선택 후에도 현재 전투에 한해 캐릭터와 패턴을 수정할 수 있다.
- 유효한 캐릭터 5명이 없으면 전투 버튼이 비활성화된다.
- 1회/3회 전투, 캡차, 세션 재로그인, 전투 결과 표시의 기존 동작이 유지된다.
- 백엔드 API 변경 없이 기존 프리셋 API를 재사용한다.
